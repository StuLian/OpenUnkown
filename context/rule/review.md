# 评审清单与红黄绿判定标准

> 独立验证 agent 打灯时使用；也供人做最终评审参考。

## 一、黄绿红判定标准（写死，勿凭感觉）

- 🔴 **红**：验证失败，或该验的没验。
  - pytest 有失败、typecheck 报错、build 挂、import 失败；
  - 验收标准（proposal 第 2 节）有未达成项；
  - 关键路径（安全/加密/DB/并发）完全没验。
  → **必停**：不修不往下走，停下问人。

- 🟡 **黄**：验证过了，但存在信息缺口。
  - 测试通过但变更点没有对应测试覆盖；
  - 有并发/边界/安全未验；
  - 代码里出现【推理生成】标注、或 agent 自述「不确定」；
  - proposal 的「风险点」在本轮未排除。
  → **不强制阻塞**：列出风险清单 + 影响面，由人决定「修 / 接受风险继续」。

- 🟢 **绿**：机器验证全绿 **且** 覆盖满足最低门槛。

## 二、绿灯门槛（「覆盖充分」的最低标准）

> 绿 = 机器验证全绿 + 变更点有对应测试覆盖。变更点若无对应测试，最高只能打黄。

| 改动类型 | 达标条件 |
|---------|---------|
| 逻辑/算法 | 至少 1 条对应 pytest 用例，且全绿 |
| 接口/路由 | typecheck 通过 + 能 import 启动 + 相关测试过 |
| 安全/加密/DB | 测试之外，强制 1 条人工审查项 |

## 三、评审清单（逐条过）

| 维度 | 要问 |
|------|------|
| 安全 | 有无鉴权绕过？密钥/DEK 是否可能明文落盘或进日志？有无注入？ |
| 边界 | 空值/类型错/超大输入/并发下会不会崩？ |
| 数据 | 表结构是否被破坏？迁移是否幂等？失败是否留半截数据？ |
| 行为 | 是否悄悄改了旧接口返回格式？（最坑前端） |
| 约定 | 是否违反 AGENTS.md 第 6 节？是否引入不必要依赖？文件是否超 300 行？ |
| 测试 | 它自称「验证过」的证据在哪？真的跑了吗？ |

## 四、校准（bug 回溯后回写本节）

- 命中的黄灯反复应验 → 把该类风险从「黄」升级为「黄必停 / 红」；
- 虚绿的盲区 → 补进第二节绿灯门槛；
- 无记录 → 流程漏洞，提醒补记录。
