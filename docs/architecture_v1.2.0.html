0V1.2.0 变更摘要

V1.1.0 完成了「让 Agent 能干活」的功能建设，但随之带来了 token 开销失控的问题：首轮闲聊即 ~2800 token（工具 schema 底噪），长对话可达 40000+ token（上下文膨胀）。V1.2.0 是一次性能优化专项，核心目标是将 token 开销降至合理水平，同时重构提示词管理，借鉴 OpenManus 的 prompt 分层架构。

  • [优化] MCP 工具列表缓存：按 Server 配置指纹缓存工具元数据，避免每次请求都冷启动子进程拉取。
  • [优化] 飞书 skill 描述瘦身：从 ~3700 字完整描述压缩到 ~800 字短目录（domain: 一句话用途），且仅命中飞书关键词时才注入。
  • [优化] 上下文压缩：_compact_history 截断旧轮的超长工具返回，保留最近 16 条消息原文。
  • [优化] 工具按需绑定（关键词预筛）：闲聊时不绑任何工具 schema，命中天气/地图/飞书关键词才绑对应工具，首轮底噪从 ~2800 降至 ~400 token。
  • [重构] 提示词模板化：新建 prompts.py 集中管理所有提示词，system prompt 从 ~450 字极简至 ~120 字，删除冗余的「匹配策略」文本。
  • [重构] 身份指令合并：从 3 处重复声明合并为 1 处（末尾 identity），消除冗余。

1Token 优化：全链路分析

每轮发给模型的输入 token 由三部分组成。V1.2.0 对每部分都做了针对性优化。

组成V1.1.0（优化前）V1.2.0（优化后）
System prompt 文本 ~450 字（身份 + 工具规则 + 匹配策略）+ 飞书 3700 字 = 每轮 ~4150 字 ~120 字（身份 + 一句引导），飞书仅按需 ~800 字
工具 Schema (bind_tools) 15 个工具全量绑定，~1400 token/轮 关键词预筛：闲聊 0 个 / 天气 1-2 个 / 地图 12 个 / 飞书 1 个
历史消息 全量透传，无压缩上限 旧工具结果截断至 240 字，尾部 16 条保原文

2工具按需绑定（关键词预筛）

V1.1.0 的 bind_tools 把全部工具的 JSON Schema 每轮都发给模型。高德 MCP 一家就 12 个工具，即使用户只说「你好」也带上 ~1400 token 的 schema 底噪。

V1.2.0 在 _chat_node 中引入关键词预筛：先取用户最新消息文本，命中哪类关键词才绑定对应工具。

2.1 关键词分组

分组关键词示例命中后绑定的工具
weather天气、气温、下雨、多少度...get_weather + maps_weather
map路线、导航、附近、高德、怎么走...全部 maps_* 工具
feishu飞书、文档、日历、待办、feishu.cn...lark_cli
未归类 MCP（用户点名服务或工具名 token 命中）对应 MCP 工具

对于未归类的自定义 MCP 工具（如用户自建的计算器 MCP），通过 _mcp_tool_hit 做兜底匹配：解析描述里的 [MCP: 服务名]，或匹配工具名中 >= 3 字符的 token。

2.2 效果对比

场景V1.1.0 绑定工具数V1.2.0 绑定工具数省掉的 schema token
闲聊「你好」150~1400
「今天天气怎么样」152~1200
「读这个飞书文档」151~1300
「从北京到上海怎么走」1512~200
工具预筛只影响 bind_tools（模型能调的工具），_tools_node 仍使用全量工具 map 做执行映射，确保安全。

3提示词模板化重构

借鉴 OpenManus 的 prompt 分层架构，将所有提示词文本从业务代码中抽出，集中管理于 backend/agent/prompts.py。

3.2 prompts.py 结构

├── IDENTITY_PROMPT    # 模型身份覆盖（{model_name} 占位符，放在历史之后）

3.3 prompt 瘦身效果

V1.1.0 base prompt（~450 字，每轮拼）：

你是 OpenUnknown 的智能助手...你由大模型 xxx 驱动...
当用户询问你的模型或身份时...历史对话里如果出现过其他模型名...
## 工具使用规则
你可以使用工具...每个工具的 description 以 [MCP: 服务名] 开头...
核心原则：当用户的意图能被任何已绑定的工具满足时，必须调用工具...
匹配策略：
1. 用户明确指定来源...
2. 用户意图与某个工具的 description 语义匹配...
3. 多个工具都能满足时，优先 MCP 工具...
4. 需要多步骤时可连续调用多个工具...

V1.2.0 SYSTEM_PROMPT（~120 字，模板）：

你是 {app_name} 的智能助手，一个乐于助人、诚实、严谨的问答助理。
请用简洁清晰的语言回答用户的问题，遇到不确定的内容要如实说明。
你可以使用工具来获取实时信息或执行操作。
当用户的意图能被已绑定的工具满足时，必须调用工具，不要凭空编造。
需要多步骤时可连续调用多个工具。

删掉了什么：

  • 身份声明（→ 移到末尾 IDENTITY_PROMPT，只保留一处）
  • 「匹配策略 1/2/3/4」（→ 交给 FC 的 tool description 自动匹配，prompt 不重复列）
  • 「[MCP: 服务名] 开头」的说明（→ 模型自己看 description 前缀即可）
核心原则：Prompt 只负责「你是谁 + 行为准则」，工具能力交给 FC schema 描述，不在 prompt 文本里重复。

4飞书 Skill 描述优化

V1.1.0 把 27 个飞书 skill 的完整描述（~3700 字）每轮注入 system prompt。V1.2.0 做了两层优化：

4.1 描述瘦身：完整描述 → 短目录

load_skill_descriptions() 现在只返回 domain 路由表的数据行（每个 domain 一行 - domain: 一句话用途），共约 ~500 字。头部的使用说明模板在 prompts.py 的 LARK_SECTION 中定义（~300 字）。

# prompts.py LARK_SECTION 模板（固定部分）
## 飞书 CLI 能力
所有飞书操作只通过工具 lark_cli...
调用：lark_cli(command="  [flags]")。
不确定子命令时必须先 lark_cli(command=" --help")...
domain 目录：
{domain_list}     <-- 动态填充
示例：不确定读文档命令时先 lark_cli(command="docs --help")...

4.2 按需注入：关键词门控

_get_system_prompt(include_lark) 只在 _FEISHU_KWS 关键词命中时才追加 LARK_SECTION。用户说「你好」→ 不带飞书目录；用户说「帮我看看飞书文档」→ 追加。

SYSTEM_PROMPT.format(app_name=...)
~120 字，每轮 +（仅命中飞书意图时） LARK_SECTION.format(domain_list=...)
~800 字，按需
_lark_domain_list 进程内缓存一次，后续直接拼接，无重复子进程开销。

5MCP 工具列表缓存

V1.1.0 的问题：每次 _chat_node 调用都重新连接所有已启用 MCP Server 拉取工具列表，npx 冷启动 Node 进程开销大。

V1.2.0 在 mcp/manager.py 中引入按 Server 配置指纹缓存：

5.1 缓存机制

graph LR
    REQ["_chat_node 请求工具列表"] --> CHK{"_meta_cache 命中?
指纹匹配?"}
    CHK --"命中"--> USE["直接返回缓存的工具元数据"]
    CHK --"未命中"--> CONN["连接 MCP Server"]
    CONN --> LIST["session.list_tools()"]
    LIST --> SAVE["缓存到 _meta_cache
(server_id -> (指纹, 元数据))"]
    SAVE --> USE

    INV["保存/删除/导入 MCP 配置"] --> CLR["invalidate_mcp_cache()"]
    CLR --> CHK

5.2 关键实现

  • 指纹计算：_server_fingerprint(cfg) 对 server_type / command / args / env / url 做 JSON 序列化，配置变了才失效。
  • 失效时机：main.py 中保存、删除、导入 MCP 配置时调用 invalidate_mcp_cache()。
  • 清理机制：_prune_stale_cache(alive_ids) 在每次请求时清掉已删除 Server 的缓存条目。
效果：首次请求仍需冷启动（不可避免），但同一配置后续请求直接走缓存，延迟从 ~2-5s 降至 <1ms。

6上下文压缩

长对话中，历史消息会线性膨胀。特别是工具返回（如 lark_cli docs --help 输出 3000+ 字），每轮都全量发给模型，导致 token 爆炸。

6.1 压缩策略：_compact_history

graph TD
    MSG["state.messages (checkpoint 原文)"] --> SPLIT{"len > KEEP_TAIL ?"}
    SPLIT --"否"--> PASS["直接返回原文"]
    SPLIT --"是"--> HEAD["head = messages[:-16]"]
    SPLIT --"是"--> TAIL["tail = messages[-16:] (保留原文)"]
    HEAD --> LOOP["遍历 head"]
    LOOP --> CHK{"msg.type == tool
且 len > 240 字?"}
    CHK --"是"--> TRUNC["截断至 240 字 + '...(已截断)'"]
    CHK --"否"--> KEEP["保留原文"]
    TRUNC --> OUT["compacted"]
    KEEP --> OUT
    OUT --> MERGE["compacted + tail"]
    TAIL --> MERGE
    MERGE --> LLM["发给 LLM"]

6.2 参数设计

参数值含义
_KEEP_TAIL16最近 16 条消息保持原文（覆盖当前工具轮）
_OLD_TOOL_CHARS240更早的 tool 消息截断到 240 字

6.3 设计要点

  • 只压缩 tool 消息：human 和 ai 消息不截断，保持对话连贯。
  • 只压缩 LLM 输入：checkpoint 中存的仍是完整原文，压缩只作用于本轮送模型的 messages。
  • tool_call_id 配对不受影响：截断只改内容不删消息，tool_call / tool_result 配对关系保持。
日志 [LLM 输入] 历史压缩 X 字 -> Y 字 可量化每轮的压缩效果。

9关键设计决策

  • 工具能力不写进 prompt：删除「匹配策略 1/2/3/4」，信任 FC 的 tool description + schema 足以引导模型选对工具。prompt 只负责行为准则。
  • 关键词预筛而非两阶段模型判断：零额外模型调用、零延迟、零成本，虽不如让模型判断灵活，但闲聊/天气/地图/飞书四大场景覆盖率足够。
  • 未归类 MCP 工具兜底匹配：通过解析 [MCP: 服务名] + 工具名 token 命中，确保用户自定义 MCP 仍可达。
  • 身份指令放在末尾：LLM 更关注最近的指令，identity 放在全部历史之后比放在 system 前面更可靠地覆盖旧模型名。
  • 压缩只动 tool 消息：工具返回往往是大段 JSON/help 文本，截断后丢失的是细节不是意图。human/ai 消息保持完整，不破坏对话逻辑。
  • MCP 缓存按指纹而非定时刷新：配置不变就不刷新，配置变了（保存/删除/导入）立即失效。简单、确定性高。

10待优化清单

问题 1：历史消息无 token 预算上限
_compact_history 只截断旧 tool 消息，对 human/ai 无限制。几十轮后 human+ai 累积仍线性增长，无全局 token 预算控制。
优化方向：对 head 部分增加总字符预算（如 8000 字），超出则按从旧到新逐轮丢弃。
问题 2：尾部窗口按条数而非 token
_KEEP_TAIL=16 是消息条数。如果最近一轮连续调用多个工具（如先 --help 再多次调用），尾部 tool 原文全保留，单轮可能顶几万 token。
优化方向：对 tail 也加 token 预算，或尾部 tool 超长时也截断。
问题 3：MCP 工具执行仍需每次重连
工具列表已缓存，但实际执行工具时仍会新建连接（连一次 → call_tool → 断开）。stdio 类 Server 的 npx 冷启动开销仍在。
优化方向：维持长连接 session 池复用，或切换为 SSE/HTTP 传输避免进程启停。
