0V1.7.0 变更摘要

V1.6.0 补齐了前端渲染与文件解析，但两个「兜底」问题还在：意图识别仍是关键词硬匹配（子串命中才算数，改写一多就漏绑工具），飞书写操作没有人工闸门（模型说要建文档/发消息就真执行，出错或越权没有二次确认）。V1.7.0 做两件事：用语意路由补齐关键词的漏召回，用飞书写操作人工确认给所有写/高危写加一道用户批准闸门。

  • [新增] 语意路由：新增 backend/agent/router.py，关键词快速通道（命中即绑定、零延迟零成本）+ text-embedding-v3 语义召回兜底；未命中时只回退关键词结果，不把全量工具 schema 绑给闲聊。
  • [新增] 飞书写操作人工确认：lark_cli 风险分级（read/write/high-risk-write）+ LangGraph interrupt() 暂停图 + 前端确认卡片 + POST /api/chat/confirm 恢复执行；写/高危写必须先经用户批准。
  • [调整] 工具绑定预筛：graph.py 的 _chat_node 改为先 route_intents 再 _select_tools，闲聊不绑工具、命中才绑对应工具。

2语意路由（工具意图预筛）

V1.6.0 里「绑不绑工具」靠关键词硬匹配：关键词 in 文本 子串命中才算数。这种写法零成本，但漏召回严重——「明天上海冷吗」命中不了关键词「冷不冷」，用户换个说法工具就绑不上。V1.7.0 新增 backend/agent/router.py，把关键词降级为高精度快速通道，未命中时用 text-embedding-v3 做语义召回兜底，既补齐改写漏召回，又保住「闲聊不绑工具」的 token 收益。

2.1 关键词快速通道

五个意图组各维护一组关键词，命中即绑定对应工具，同步、零网络、零额外延迟。只放「高置信、低歧义」的显式表达，其余改写交给语义锚点。

# backend/agent/router.py —— 关键词快速通道（命中即绑定）
_KEYWORD_MAP = {
    "weather": ("天气", "气温", "冷不冷", "下雨", "多少度", ...),
    "map":     ("地图", "路线", "导航", "怎么走", "附近", "高德", ...),
    "feishu":  ("飞书", "文档", "多维表格", "日程", "邮件", "云盘", ...),
    "browse":  ("网页", "搜索", "新闻", "股价", "热搜", ...),
    "hotel":   ("酒店", "住宿", "订房", "西雅图", "民宿", ...),
}

2.2 语义锚点与召回兜底

关键词没命中且文本非空时，才把查询向量化，与各意图的语义锚点（每组一组代表性问法）做余弦相似度。锚点是「数据」而非「规则」——漏召回时补一句样例，而不是再想一个关键词。

# 语义锚点：覆盖常见改写，而非罗列关键词
_ANCHORS = {
    "weather": ("今天冷不冷", "明天会下雨吗", "出门要不要带伞", "上海明天冷吗", ...),
    "feishu":  ("帮我查飞书文档", "今天有什么会议", "我的待办任务有哪些", ...),
    ...
}

2.3 阈值校准（勿拍脑袋调）

短中文的基线余弦相似度约 0.5，只设一个绝对阈值会连「给我讲个笑话」都绑上全部工具。实测：真意图锚点相似度 ≥ 0.86 且领先第二名 ≥ 0.24；闲聊 top1 ≤ 0.64、领先 ≤ 0.10。因此要求「绝对分数够高 且 明显领先第二名」才算命中。

_SIM_FLOOR = 0.75   # 绝对下限：真意图 >= 0.86，闲聊/裸城市 <= 0.66
_SIM_MARGIN = 0.15  # 领先第二名边距：真意图 >= 0.24，闲聊/裸城市 <= 0.10

锚点向量按需懒加载并缓存：embedding 模型与平台全局一致、与具体用户无关，任一用户首次触发后即可复用（仅查询向量每次按当前用户 ApiKey 现算）。embed_texts 沿用酒店 RAG 的 text-embedding-v3（1024 维），query 文本类型共享同一向量空间。

2.4 多轮继承与失败回退

短跟随消息（≤ 5 字，如只补一个城市名「北京」/日期「明天」）自身表达不出意图时，继承上一轮用户意图，避免未完成的工具任务被一个补充词打断。语义召回失败不回退到全绑定，而是保持关键词结果（下轮重试），防止把闲聊也带上全部工具 schema。

# backend/agent/router.py —— 两级路由入口
async def route_intents(text, api_key, prev_user_text=""):
    want = await _route_single(text, api_key)          # 关键词 → 语义召回兜底
    if any(want.values()) or not text:
        return want
    if prev_user_text and len(text) <= _FOLLOWUP_MAX_CHARS:   # 短跟随继承
        return await _route_single(prev_user_text, api_key)
    return want

2.5 与 graph 的衔接

_chat_node 拿到本轮用户文本后先 route_intents，再 _select_tools 按命中结果绑定工具；闲聊返回空列表，不绑任何工具 schema，省掉全部工具描述的固定 token 底噪（高德一家就 12 个）。

# backend/agent/graph.py —— 按意图预筛本轮工具
want = await route_intents(user_text, api_key=api_key,
                           prev_user_text=_prev_user_text(state["messages"]))
all_tools = await _get_all_tools(user_id)
bound_tools = [] if force_answer else _select_tools(all_tools, user_text, want)
llm = llm.bind_tools(bound_tools) if bound_tools else llm
收益：闲聊/不相关时零工具 schema、零 embedding 调用；改写类问题由语义召回兜住，不再因为换个说法就漏绑工具。

3飞书写操作人工确认

飞书域能做的事很多是有副作用的写操作（发消息、建文档、写表格、发邮件、删除/撤回）。V1.6.0 里模型要写就写，没有人工闸门，出错或越权没有二次确认。V1.7.0 给所有 write / high-risk-write 命令加一道用户批准闸门：执行前先 interrupt() 暂停图，前端弹确认卡片，用户点「确认执行」才真正跑。

3.1 风险分级 classify_risk

lark-cli 每条子命令的 --help 都带一行 Risk: read | write | high-risk-write，这里以它为权威信号并缓存结果；判定不了时兜底为 write（宁可多确认一次，也不静默写入）。

# backend/agent/tools/lark_cli.py —— 风险分级（以 --help 的 Risk: 行为准）
async def classify_risk(command: str) -> str:
    if any(a in ("--help", "-h", "--dry-run") for a in args):
        return "read"                       # 帮助/试跑无副作用
    if domain in _READ_ONLY_DOMAINS:
        return "read"                       # CLI 管理类不改业务数据
    if domain == "api":
        return "read" if method == "GET" else "write"   # 裸调用按 HTTP 方法
    risk = await _risk_from_help(key_tokens)  # 拉 '<domain> <sub> --help'
    return "write" if risk == "unknown" else risk   # 未知兜底为写，绝不静默放行

3.2 interrupt 安全闸门

tools 节点在执行任何工具之前先扫描本轮 tool_calls，找到首个飞书写操作就 interrupt() 暂停。interrupt 放在所有执行之前，是因为 resume 时节点会从头部重跑——若先执行了读操作会重复执行。

# backend/agent/graph.py —— 飞书安全闸门（执行前先中断等确认）
for tc in tool_calls:
    if tc.get("name") != "lark_cli":
        continue
    command = (tc.get("args") or {}).get("command", "")
    if await classify_risk(command) in ("write", "high-risk-write"):
        decision = interrupt({
            "type": "lark_write_confirmation",
            "tool_call_id": tc.get("id"),
            "command": command,
            "risk": risk,
        })
        break

确认通过后，high-risk-write 命令由 ensure_yes() 自动补 --yes（lark-cli 约定「agent 不得自行加 --yes，只能用户确认后加」——用户批准即等价授权）；未确认则返回「已取消」给模型，由模型向用户说明并询问是否重试。

3.3 确认与恢复链路（SSE + /chat/confirm）

图在 interrupt 处停住后，streaming.py 检测到待确认状态，产出 confirm 事件给前端；用户决策后经 POST /api/chat/confirm 从 checkpoint 恢复图并继续流式输出剩余回答。

tools 节点 interrupt 暂停→ SSE 推送 confirm 事件→ 前端弹确认卡片→ POST /api/chat/confirm→ Command(resume={approved}) 恢复→ 执行 lark_cli / 取消 
# backend/api/streaming.py —— 确认事件检测 + 恢复
async def _pending_confirm(graph, config):      # 图停在写操作 interrupt 上？
    for task in state.tasks:
        for iv in task.interrupts:
            if iv.value.get("type") == "lark_write_confirmation":
                return iv.value

# 图停在待确认处时产出 confirm 事件，轮次未完成不产 usage
confirm = await _pending_confirm(graph, config)
if confirm is not None:
    yield {"confirm": confirm}

# resume_answer —— 确认后从 checkpoint 恢复
Command(resume={"approved": bool(approved)})

3.4 前端确认卡片

前端 ChatView.tsx 收到 confirm 事件后置 pendingConfirm，气泡内渲染确认卡片（风险级别 + 完整命令 + 确认/取消按钮）；用户点「停止」视为取消该写操作。决策后递归调用 /api/chat/confirm 恢复后续流。

// frontend/src/components/ChatView.tsx —— 确认卡片渲染（节选）
if (ev.confirm) {
  patch({ pendingConfirm: { command: ev.confirm.command, risk: ev.confirm.risk } });
  const approved = await new Promise<boolean>((resolve) => (decideRef.current = resolve));
  patch({ pendingConfirm: null });
  await streamTurn("/api/chat/confirm", { session_id: sessionId, approved, ... });
  return;
}
残留清理：用户中途刷新/切换会话后重发，上一轮可能残留未确认的写操作。_drain_pending_confirm 会在新消息前检测并自动以 approved=False 取消跑完，保证 checkpoint 干净、不阻塞后续新消息。

5关键设计决策

  • 关键词降级为「高精度快速通道」，而非直接删除：命中即绑定、零延迟零成本，承担高置信显式表达；语义召回只在未命中时兜底，避免每轮都付一次 embedding 调用。
  • 锚点是数据不是规则：每组一组代表性问法，漏召回时补一句样例，而不是再想一个关键词——新增覆盖成本极低，且天然覆盖「改写」而非罗列词面。
  • 语义命中要求「绝对分数高 且 明显领先」：用真实 text-embedding-v3 数据校准阈值，避免裸城市名/闲聊这类弱信号把五个工具组全绑上；弱信号交给多轮继承兜底。
  • embedding 失败不回退到全绑定：宁可本轮少绑工具（下轮重试），也不把闲聊带上全部工具 schema，守住「闲聊零底噪」的收益。
  • 风险分级以 --help 的 Risk: 行为权威信号并缓存：不与 lark-cli 的判定漂移，未知一律按 write 处理（宁多确认一次，不静默写入）。
  • interrupt 放在所有工具执行之前：resume 时节点从头部重跑，若先执行了读操作会重复执行；先中断再放行，保证「只执行一次」。
  • --yes 由系统在用户确认后补，模型不得自行加：遵守 lark-cli 的授权约定，用户批准即等价授权，避免模型绕过确认闸门。
  • 残留确认自动取消：刷新/切换会话后的孤儿 interrupt 由 _drain_pending_confirm 以 approved=False 静默清理，保证 checkpoint 干净、不阻塞后续消息。

6待优化清单

问题 1：语义召回每次都现算查询向量，长会话里开销累积
每次未命中关键词都要调一次 embedding，多轮对话可能反复触发。
优化方向：对最近几轮已路由过的查询做向量缓存，或把「明显闲聊」的短句直接判定为不路由、跳过 embedding。
问题 2：锚点样例有限，长尾意图覆盖不全
五个意图组共 36 条锚点，冷门说法仍可能漏召回。
优化方向：按真实线上漏召回日志持续补充锚点，或引入轻量改写/同义扩充，让锚点自动泛化。
问题 3：风险分级依赖拉取 --help，首次判定有一拍延迟
未缓存的命令要先跑一次 --help 才拿到 Risk，写操作确认链路因此多一跳。
优化方向：启动时预热常用命令的风险缓存，或让 lark-cli 提供一次性风险清单批量导入。
问题 4：确认卡片只有「确认/取消」，无法预览写操作影响范围
用户看不到这条写命令会改动什么（收件人、文档内容、删除对象）。
优化方向：interrupt 负载里附带命令的「影响摘要」（如目标文档/收件人），前端卡片先预览再决定。
问题 5：写操作确认无细粒度豁免
同一会话内反复同类写操作仍逐次确认，体验偏繁琐。
优化方向：支持「本次会话信任该命令」的临时豁免，或按风险级别/域配置确认策略。
