0V1.6.0 变更摘要

V1.5.0 补齐了追踪、密钥治理与集成部署，但应用仍停留在「纯文本问答」：前端还由 FastAPI 直接托管静态页，模型返回的图片链接只是一行文字、mermaid 代码块只是源码，用户也没法把本地文档喂给模型。V1.6.0 做了四件事：用 React 重构前端、让 Markdown 能渲染图片与 mermaid 图谱、支持上传文件并解析为可参与问答的内容，并为 AI 协作者沉淀项目地图（AGENTS.md + CLAUDE.md）。

  • [重构] React 前端重构：React 18 + TypeScript + Vite，手写组件、无 UI 框架；dev.sh 一键起前后端，dist/ 构建产物不入库。
  • [新增] 图片与 Mermaid 图谱渲染：react-markdown + remark-gfm 渲染 Markdown，裸图片链接自动识别成图片，mermaid 懒加载渲染并支持点击预览、缩放、平移。
  • [新增] 文件上传与解析：txt/md/csv/pdf/docx/xlsx 解析为纯文本，图片校验缩放后编码，发送时调用视觉模型 OCR，一并注入对话上下文。
  • [新增] Agent.md 与 Claude.md：AGENTS.md 项目地图 + CLAUDE.md 转发，scripts/gen_agents_doc.py 自动刷新 + pre-commit 钩子纳入提交。

2React 前端重构

V1.5.0 之前前端是 FastAPI 直接托管的静态页，交互状态散落、难以维护。V1.6.0 用 React 18 + TypeScript + Vite 重建前端，手写组件、不引 UI 框架，把职责拆成四层：组件、上下文、api client、本地库。

2.1 目录结构

frontend/
├── index.html / vite.config.ts / tsconfig.json   # Vite 与 TS 配置
└── src/
    ├── components/          # ChatView / Markdown / Sidebar / SettingsModal / McpModal / AuthOverlay / Modal
    ├── context/AuthContext.tsx   # 登录态上下文（当前用户 / 加载 / 登录登出）
    ├── api/                 # client.ts（fetch 封装）+ endpoints.ts（接口定义）
    ├── lib/                 # crypto.ts（RSA-OAEP 密码加密）/ sse.ts（SSE 流式）/ storage.ts（本地存储）
    ├── App.tsx / main.tsx / styles.css / types.ts

2.2 与后端的衔接

前端不直接发模型请求，所有交互都走 /api/*：登录走 /api/auth，对话走 /api/chat 的 SSE 流式，附件走 /api/files。开发时 Vite 把 /api 代理到后端 :8000；生产时 npm run build 产物落到 frontend/dist，由 FastAPI 托管（dist/ 不入库）。

# dev.sh —— 一键开发环境（后端 reload + 前端 HMR）
.venv/bin/uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000 &
cd frontend && npm run dev   # /api 代理到 8000
收益：组件化后 Markdown 渲染、附件上传、设置弹窗各自独立，流式期间的消息增量更新（useEffect + SSE 解析）不再依赖整页重绘，交互提示也更顺滑。

3图片与 Mermaid 图谱渲染

V1.5.0 里模型输出的 Markdown 是「原样文本」：图片链接不显示图、```mermaid 只显示源码。V1.6.0 在 frontend/src/components/Markdown.tsx 里用 react-markdown 统一渲染，并挂了两个能力。

3.1 Markdown 渲染（GFM + 换行）

// Markdown.tsx —— react-markdown + remark-gfm + remark-breaks
<ReactMarkdown
  remarkPlugins={[remarkGfm, remarkBreaks, ...(autoImageLinks ? [remarkBareImageLinks] : [])]}
  urlTransform={urlTransform}
  components={components}
>

3.2 裸图片链接自动识别

自定义 remarkBareImageLinks 插件遍历 MDAST：GFM 已把裸链接转成 <a>，若链接文本就是 URL 本身、且扩展名（或查询参数）看起来像图片，就替换成 image 节点。用户 query 里的裸链接不识别（autoImageLinks=false），只在助手回答里自动出图。

// 图片 URL 白名单：png/jpg/jpeg/gif/webp/svg/bmp/avif/ico
// 无扩展名时按查询参数 format/fmt/f/type 判断
const IMAGE_EXTENSIONS = ["png","jpg","jpeg","gif","webp","svg","bmp","avif","ico"];

3.3 安全：URL 协议白名单

渲染层用 urlTransform 拦截危险协议：javascript: / vbscript: / data:text/html 直接置空，普通 data:（内联图片）放行，其余走 react-markdown 默认策略。图片点击仅对 http(s) 才新标签打开原图。

3.4 Mermaid 图谱渲染

mermaid 通过动态 import("mermaid") 懒加载并只初始化一次（不出现图谱不拉包）；流式期间内容高频变化，渲染做 300ms 去抖，失败则回退展示源码。渲染成功后点开 lightbox 预览，支持滚轮/捏合缩放与拖拽平移。

// MermaidBlock —— 懒加载 + 去抖 + 失败回退 + lightbox 预览
const timer = window.setTimeout(async () => {
  const mermaid = await loadMermaid();
  const result = await mermaid.render(nextMermaidId(), trimmed);   // 全局唯一容器 id
  setSvg(result.svg);
}, 300);   // 流式期间去抖，避免反复解析不完整语法
踩坑记录：mermaid 渲染必须用全局唯一容器 id（mmd-<counter>-<time>），否则多次渲染互相覆盖；SVG 预览缩放用 viewBox 而非改 width/height，避免大图被缩得太小。

4文件上传与解析

V1.6.0 新增 backend/files/ 模块与 /api/files 路由：文档/表格上传后解析为纯文本，图片上传后仅编码（校验 + 缩放），OCR 延迟到真正发送消息时执行，避免「上传即调模型」的浪费。粘贴链接（POST /url）下载内容后走同一套解析流程。

4.1 文档解析（parser.py）

格式解析方式依赖
txt / md / markdown按编码回退解码（utf-8-sig → gb18030 → latin-1）内置
csvcsv.Sniffer 探测分隔符，转成易读表格文本内置
pdf逐页提取文本（最多 200 页）pypdf
docx段落 + 表格逐行提取python-docx
xlsx按工作表逐行转文本（最多 2000 行）openpyxl
 
# backend/files/parser.py —— 统一限制，避免超大文件撑爆上下文
MAX_FILE_SIZE = 10 * 1024 * 1024   # 单文件 10 MB
MAX_CONTENT_CHARS = 50_000         # 注入上下文 5 万字符，超长截断
MAX_TABLE_ROWS = 2_000             # CSV/XLSX 最大行数
MAX_PDF_PAGES = 200                # PDF 最大页数

三个解析库均为可选依赖，函数内延迟 import：缺库时抛 ParseError 提示，不影响应用启动。解析结果统一为纯文本并做长度截断，返回 ParsedFile（文件名/类型/大小/内容/是否截断）。

4.2 图片处理（image.py）

图片是二进制像素，无法「解析成文字」，这里做两件事：用 Pillow 校验并限制长边（2048px）后编码为 data URL 供前端预览与模型看图；另提供 ocr_image() 调用视觉模型把图中文字提取为文本。

# backend/files/image.py
MAX_IMAGE_SIZE = 8 * 1024 * 1024    # 单图 8 MB
MAX_IMAGE_EDGE = 2048               # 长边上限，超出等比缩小
OCR_TIMEOUT = 60.0                  # OCR 调用超时
VISION_MODEL = "qwen-vl-plus"       # 视觉（多模态）模型，见 backend/config.py

编码时按有无透明通道选格式：RGBA 用 PNG，否则用 JPEG（体积更小、视觉模型普遍支持）；GIF 等多帧图只取第一帧。OCR 用固定提示词「只输出文字本身、不要解释」+ 单张图片消息。

4.3 上传链路

前端选择/拖拽/粘贴文件→ GET /api/files/limits 本地校验→ POST /api/files 上传→ 按扩展名分发：图片编码 / 文档解析→ 返回 data URL 或解析文本 
# backend/api/routers/files.py —— 按扩展名分发
if ext in image.IMAGE_EXTENSIONS:
    img = image.process_image(filename, data)     # 校验 + 缩放 + data URL
    return { "file_type": "image", "image": img.data_url, ... }
parsed = parser.parse_bytes(filename, data)       # 文档/表格 → 纯文本
return { "file_type": parsed.file_type, "content": parsed.content, "truncated": ... }

4.4 附件注入对话（streaming.py）

发送消息时 _split_attachments 把附件拆成三类：文档文本转成系统消息（[附件 N] 用户上传了文件《xxx》，解析内容如下…）、图片走并发 OCR 后作为图片内容块注入、附件名写进 additional_kwargs.attachment_names 供前端回显。

# backend/api/streaming.py —— 图片并发 OCR + 多模态内容块
if images:
    ocr_results = await asyncio.gather(*(ocr_image(url, api_key) for _, url in images))
if image_urls:
    effective_model = VISION_MODEL                      # 有图时切视觉模型
    content_blocks.append({"type": "image_url", "image_url": {"url": url}})
效果：用户可以把 PDF/Word/Excel/CSV 直接拖进对话框，模型基于解析出的文本作答；图片则「看图 + 提取文字」双通道喂给多模态模型。

5Agent.md 与 Claude.md 项目上下文

为了让不同 AI 协作者（Claude、Codex、Agent 等）开箱即用，V1.6.0 在仓库根目录沉淀了两份项目地图，并配套自动刷新脚本与 pre-commit 钩子，保证文档跟代码同步。

5.1 两份文件

文件内容角色
AGENTS.md一句话概述、技术栈、模块职责、常用命令、API 路由表、关键约定与坑、维护说明、源码文件清单单一事实来源（给 AI 看的项目地图）

5.2 自动刷新 + pre-commit

AGENTS.md 里的依赖版本、路由表、文件清单是自动生成区域（<!-- AUTO-GEN:* --> 包裹），改代码后由脚本一键刷新，提交前钩子自动执行——手写区域不受影响。

# scripts/gen_agents_doc.py —— 只重写 AUTO-GEN 区域（DEPS / ROUTES / FILES）
python scripts/gen_agents_doc.py

# .githooks/pre-commit —— 提交前自动刷新并纳入本次提交
git config core.hooksPath .githooks      # 跳过用 git commit --no-verify
约定：模块职责（第 3 节）与「约定与坑」（第 6 节）为手写区，新增/删除模块或约定时手动更新并同步顶部日期；自动生成区域不要手改。

7关键设计决策

  • React 重构「无 UI 框架、手写组件」：只引 react / react-dom，组件自研，避免引入整套组件库的包体与样式约束，便于贴合深色主题与流式交互。
  • 渲染层「协议白名单 + data:image 放行」：urlTransform 拦截 javascript: 等危险协议，只对 http(s) 开新标签、对 data: 图片放行，兼顾 Markdown 富文本与 XSS 防护。
  • mermaid「懒加载 + 去抖 + 失败回退」：动态 import 减小首屏包体，流式期间 300ms 去抖避免解析不完整语法，渲染失败回退展示源码——图谱是增强不是必需。
  • 图片 OCR「延迟到发送时」：上传只校验缩放编码，不调用模型；真正发送时才并发 OCR。避免「传了没用」的模型调用浪费。
  • 附件「统一解析为纯文本注入」：PDF/Word/Excel 都先转成纯文本、截断后作为系统消息注入，模型无需理解二进制，也天然限制上下文长度。
  • 可选解析依赖「函数内延迟 import」：pypdf / python-docx / openpyxl / Pillow 按需加载，缺库只影响对应格式解析，不拖累应用启动。
  • CLAUDE.md「只做转发指针」：内容全部收敛到 AGENTS.md 一份，避免两份文档漂移；其余 AI 协作者通过标准约定直接读 AGENTS.md。
  • 自动生成区域「脚本刷新 + 提交钩子兜底」：依赖/路由/文件清单由 gen_agents_doc.py 生成，pre-commit 自动执行，杜绝「代码改了文档没跟」的漂移。

8待优化清单

问题 1：mermaid 图谱在客户端渲染，复杂图可能卡顿
大图谱在浏览器里解析/布局可能耗时，流式期间反复去抖渲染也有开销。
优化方向：对超大图谱降级为源码 + 手动展开，或把渲染结果做 memo 缓存；必要时服务端预渲染 SVG。
问题 2：图片 OCR 每次发送都重新调用
同一张图片重复发送会重复调视觉模型，既慢又费 token。
优化方向：按图片 hash 缓存 OCR 结果，或上传后即后台预 OCR，发送时直接复用。
问题 3：文档解析为纯文本，丢失格式与结构
表格被压成 | 分隔、层级与样式丢失，复杂排版会失真。
优化方向：对表格保留 Markdown 表格/结构化 JSON，或对关键文档走向量检索而非整段注入。
问题 4：图片格式支持有限
目前仅 jpg/jpeg/png/webp/gif，heic/tiff 等常见格式不支持。
优化方向：扩充分支并做格式归一（如 HEIC→JPEG），或在客户端先转码再上传。
问题 5：附件随消息重发重复占用上下文
附件解析文本是「内联注入」到每次请求，长对话里反复携带会撑满上下文窗口。
优化方向：附件解析结果落库并生成引用 id，消息只引用 id，由后端按需拼装。
问题 6：AGENTS.md 自动刷新依赖脚本/钩子，缺一道 CI 校验
pre-commit 可被 --no-verify 跳过，长期仍可能漂移。
优化方向：加 CI 步骤跑 gen_agents_doc.py 并 diff 校验，漂移即失败。
