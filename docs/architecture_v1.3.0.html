0V1.3.0 变更摘要

V1.2.0 解决了 token 开销与工具按需绑定问题，但 Agent 的「对外信息获取」能力仍局限在天气与飞书两个域：既不能抓取用户给出的网页，也不能联网搜索时事资讯。V1.3.0 补齐了浏览器能力——新增 browser_fetch / browser_search 两个工具，沿用 V1.2.0 的关键词预筛机制按需触发；同时针对工具反复失败导致的死循环问题，引入工具调用上限保证图一定能收敛。

  • [新增] browser_fetch 网页抓取：抓取指定 URL 并提取可读纯文本（标题/摘要/正文），用标准库 html.parser 抽取，正文上限 4000 字。
  • [新增] browser_search 联网搜索：DuckDuckGo HTML 为主源、Bing 网页搜索兜底，无需 API Key，自动过滤广告并解码重定向 URL。
  • [新增] 浏览意图关键词预筛：_BROWSE_KWS 关键词组 + want["browse"] 标志，命中「搜索/网页/网址/新闻」等才绑定浏览器工具。
  • [修复] 工具调用上限：MAX_TOOL_CALLS = 8 + _tool_calls_this_turn()，单轮工具调用超限后强制模型直接作答，杜绝 recursion limit 死循环。

1浏览器工具总览

新增模块 backend/agent/tools/browser_use.py，设计上刻意对齐 weather.py 的轻量范式：只用项目已有的 httpx + Python 标准库，不引入无头浏览器、不启动额外进程、不需要任何 API Key。

两个工具分别覆盖「给网址 → 读内容」和「给关键词 → 搜结果」两种浏览意图：

工具输入做什么典型问法
browser_fetchurl抓取网页 → 提取标题/摘要/正文纯文本「打开这个网页」「抓取这个网址的内容」
browser_searchquery + max_results联网搜索 → 返回标题/真实 URL/摘要列表「搜索一下」「搜一下 XX 最新消息」
设计原则延续 V1.2.0：工具能力写进 FC schema（docstring），不在 prompt 里重复。两个工具的描述字段直接引导模型在「搜」和「抓」之间选择。

2browser_fetch：网页正文提取

browser_fetch(url) 的职责是把任意 HTML 网页压缩成模型可读的纯文本，核心是 _TextExtractor(HTMLParser)——继承标准库 html.parser.HTMLParser，不引入 BeautifulSoup / readability 等第三方解析库。

2.1 提取策略

class _TextExtractor(HTMLParser):
    _SKIP_TAGS  = {"script","style","noscript","template","svg","iframe"}   # 不可见内容直接丢弃
    _BLOCK_TAGS = {"p","div","li","h1"..."section","article","table",...}   # 块级标签换行

    # 记录三类信息：
    #   title        标签文本
    #   description <meta name="description" content="...">
    #   body        块级标签分段后的正文文本</code></pre>
      <p>拼装输出顺序为 <code>标题 → 摘要 → 正文</code>，正文若超过 <code>_MAX_TEXT=4000</code> 字则截断并标注，避免长页面撑爆上下文。</p>

      <h3>2.2 关键实现点</h3>
      <ul>
        <li><strong>URL 归一化</strong>：<code>_normalize_url()</code> 自动给缺协议的 <code>example.com</code> 补 <code>https://</code>，用户随手丢域名也能抓。</li>
        <li><strong>伪装浏览器</strong>：统一 <code>User-Agent</code> + <code>Accept-Language: zh-CN</code>，降低站点反爬拦截概率。</li>
        <li><strong>容错返回</strong>：抓取异常或正文为空时返回明确的字符串错误（如「未提取到正文，可能是 JS 动态渲染或反爬页面」），不抛异常打断工具节点。</li>
      </ul>
    </section>

    <section>
      <h2><span class="num">3</span>browser_search：联网搜索（多源兜底）</h2>
      <p><code>browser_search(query, max_results=5)</code> 提供无 Key 的联网检索。第一版只接了 DuckDuckGo HTML 端点，实测连续请求几次后会被返回 202 挑战页（限流），导致工具空手而归、模型反复重试。因此 V1.3.0 设计成<strong>双源兜底</strong>结构。</p>

      <h3>3.1 搜索链路</h3>
      <pre class="mermaid">
graph LR
    Q["browser_search(query, max_results)"] --> DDG["_ddg_search<br/>DuckDuckGo HTML"]
    DDG --"有结果"--> FMT["格式化 title/url/snippet"]
    DDG --"空结果/异常"--> BING["_bing_search<br/>Bing 网页搜索兜底"]
    BING --> FMT
    FMT --> OUT["返回结果列表"]
      </pre>
      <p><code>_web_search()</code> 封装了这个回退逻辑：先试 DuckDuckGo，空结果或抛异常就切 Bing，二者都失败才返回「搜索引擎暂时不可用」。</p>

      <h3>3.2 结果清洗</h3>
      <ul>
        <li><strong>广告过滤</strong>：DuckDuckGo 结果里的广告位是 <code>duckduckgo.com/y.js</code> 或 bing <code>aclick</code> 重定向，<code>_is_ad_href()</code> 识别后整条跳过。</li>
        <li><strong>URL 解码</strong>：DDG 的 <code>//duckduckgo.com/l/?uddg=<编码></code> 与 Bing 的 <code>/ck/a?...&u=a1<base64></code> 都是重定向壳，分别用 <code>unquote</code> 和 <code>base64.urlsafe_b64decode</code> 还原真实目标 URL。</li>
        <li><strong>条数钳制</strong>：<code>max_results</code> 限制在 1–10 之间，防止模型要 100 条拖垮返回。</li>
      </ul>
      <div class="note">两个解析器（<code>_DDGResultParser</code> / <code>_bing_search</code> 的块分割）都用标准库 <code>HTMLParser</code> / <code>re</code> 实现，无新增第三方依赖。</div>
    </section>

    <section>
      <h2><span class="num">4</span>触发机制：浏览意图关键词预筛</h2>
      <p>延续 V1.2.0 的 <code>_select_tools</code> 预筛思路，新增一组 <code>_BROWSE_KWS</code> 关键词，命中才绑定浏览器工具，闲聊时不增加任何 schema 底噪。</p>

      <h3>4.1 关键词分组</h3>
      <table>
        <thead><tr><th>分组</th><th>关键词示例</th><th>命中后绑定的工具</th></tr></thead>
        <tbody>
          <tr><td><span class="tag blue">weather</span></td><td>天气、气温、下雨、多少度...</td><td><code>get_weather</code></td></tr>
          <tr><td><span class="tag green">map</span></td><td>路线、导航、附近、高德...</td><td>全部 <code>maps_*</code> 工具</td></tr>
          <tr><td><span class="tag purple">feishu</span></td><td>飞书、文档、日历、待办...</td><td><code>lark_cli</code></td></tr>
          <tr><td><span class="tag pink">browse</span></td><td>网页、网址、链接、搜索、搜一下、新闻、资讯、抓取、http、search...</td><td><code>browser_fetch</code> + <code>browser_search</code></td></tr>
        </tbody>
      </table>
      <p><code>_select_tools</code> 中新增分支：<code>name in ("browser_fetch", "browser_search")</code> 且 <code>want["browse"]</code> 为真时绑定这两个工具。</p>

      <h3>4.2 两层触发：绑定 ≠ 调用</h3>
      <p>关键词命中只是<strong>第一层（绑定）</strong>，把工具 schema 交给模型；<strong>第二层（调用）</strong>由模型根据 docstring 决定到底调 <code>browser_search</code>（想搜）还是 <code>browser_fetch</code>（给了网址）。</p>
      <div class="flow">
        <span class="step">用户消息 → 小写化</span>
        <span class="arrow">→</span>
        <span class="step">_hit(text, _BROWSE_KWS)</span>
        <span class="arrow">命中 →</span>
        <span class="step">绑定 fetch + search</span>
        <span class="arrow">→</span>
        <span class="step">模型按 docstring 决定调哪个</span>
      </div>
      <div class="note">子串匹配且大小写不敏感：<code>search latest AI news</code> 与 <code>帮我搜索新闻</code> 同样命中；想让浏览器工具必触发，话里带上「搜索 / 打开网页 / 抓取」等动词即可。</div>
    </section>

    <section>
      <h2><span class="num">5</span>工具调用收敛保障</h2>
      <p>浏览器工具上线后暴露了一个健壮性问题：当 <code>browser_search</code> 被限流返回空结果时，模型会不断换着法重试（搜索 → 抓取 → 再搜索…），<code>chat → tools → chat → …</code> 循环超过 LangGraph 默认 <code>recursion_limit=25</code>，直接抛错中断。</p>

      <h3>5.1 根因</h3>
      <p>原图只有 <code>tools_condition</code> 一个终止条件：模型不再产生 tool_calls 才结束。工具一旦「永远给不出满意结果」，模型就可能「永远继续调工具」，图没有兜底出口。</p>

      <h3>5.2 方案：按轮计数 + 强制作答</h3>
      <pre><code>MAX_TOOL_CALLS = 8

def _tool_calls_this_turn(messages):
    # 只统计最近一条 human 消息之后的 tool 消息数，天然按轮重置
    count = 0
    for msg in reversed(messages):
        if msg.type == "human": break
        if msg.type == "tool": count += 1
    return count</code></pre>
      <p><code>_chat_node</code> 每次进入时用 <code>_tool_calls_this_turn()</code> 判断：达到上限则<strong>不绑任何工具</strong>，并追加一条「必须停止调用工具、直接回答」的 SystemMessage，保证下一跳必然收敛。</p>

      <h3>5.3 执行流</h3>
      <pre class="mermaid">
graph TD
    CHAT["_chat_node"] --> COUNT{"_tool_calls_this_turn()<br/>>= MAX_TOOL_CALLS ?"}
    COUNT --"否"--> BIND["正常关键词预筛 + bind_tools"]
    COUNT --"是"--> FORCE["不绑工具 + 追加强制作答指令"]
    BIND --> LLM["LLM 生成 tool_calls 或最终答案"]
    FORCE --> LLM
    LLM --"有 tool_calls"--> TOOLS["_tools_node 执行"]
    TOOLS --> CHAT
    LLM --"无 tool_calls"--> END["END"]
      </pre>

      <div class="success"><strong>关键点</strong>：计数器从「最近一条 human 消息」重新算起，因此上限是<strong>单轮</strong>的，不会跨多轮对话累积导致后面的轮次工具被误禁用。8 次工具调用对应约 18 步，远低于 recursion_limit=25。</div>
    </section>

    <section>
      <h2><span class="num">7</span>关键设计决策</h2>
      <ul>
        <li><strong>不引入 browser-use 库 / Playwright</strong>：先用 httpx + 标准库覆盖「抓网页 + 搜索」两个高频场景，零依赖、零安装成本、立即可用；无头浏览器自动化留作后续升级点，接口上预留同模块扩展空间。</li>
        <li><strong>双源搜索兜底而非单源重试</strong>：DuckDuckGo 限流是常态，单纯重试治标不治本；切到结构不同的 Bing 源才能真正拿到结果。</li>
        <li><strong>广告过滤 + URL 解码做在解析层</strong>：搜索结果直接返回真实 URL，避免模型拿着 <code>duckduckgo.com/l/?uddg=...</code> 这种重定向壳去做无用功。</li>
        <li><strong>收敛保障走「消息计数」而非独立 state 字段</strong>：从消息历史推导本轮工具次数，天然按轮重置、无需额外持久化 channel，也不会因 checkpoint 跨轮累积而出 bug。</li>
        <li><strong>触发沿用关键词预筛而非单独判断模型</strong>：与 V1.2.0 保持一致，零额外模型调用、零延迟，浏览场景关键词覆盖率足够。</li>
      </ul>
    </section>

    <section>
      <h2><span class="num">8</span>待优化清单</h2>
      <div class="todo">
        <strong>问题 1：正文提取对 JS 渲染页面失效</strong><br/>
        <code>_TextExtractor</code> 只能处理服务端直出的 HTML，SPA / 大量 JS 动态渲染的页面抓不到正文，只能返回「未提取到正文」。<br/>
        优化方向：引入真实无头浏览器（Playwright）作为 <code>browser_fetch</code> 的升级路径，或接入 <code>browser-use</code> 库支持点击/输入/导航。
      </div>
      <div class="todo">
        <strong>问题 2：搜索源仍可能同时限流</strong><br/>
        DDG 与 Bing 都是免费 HTML 端点，无 SLA 保证，极端情况下可能同时被限流。<br/>
        优化方向：增加可配置的搜索 API（如 SerpAPI / Tavily）作为高可用兜底，或对限流响应做退避重试。
      </div>
      <div class="todo">
        <strong>问题 3：抓取无大小/超时精细控制</strong><br/>
        <code>browser_fetch</code> 会下载完整响应体再截断，超大页面（几十 MB）可能拖慢工具执行。<br/>
        优化方向：按 <code>Content-Length</code> / 流式读取提前截断，仅解析前 N KB。
      </div>
