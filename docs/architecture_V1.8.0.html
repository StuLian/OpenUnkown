0V1.8.0 变更摘要

V1.7.0 补齐了语意路由与飞书写操作人工确认，但三个「看不见、记不住、留不下」的问题还在：每轮对话没有可回放的 trace（出了错只能靠人肉复述）、RAG/prompt 质量没有量化手段（改完不知道变好还是变坏）、长会话 token 越滚越大、跨会话毫无记忆。V1.8.0 做三件事：用Trace 轨迹 + 离线评测建立可观测与测量底座，用长期记忆 + Token 预算让对话「记得住又花得起」。

  • [新增] Trace 轨迹可观测：新增 backend/tracing/collector.py（TraceCollector 采集原始报文/工具调用/召回），每轮落 runs 表并自动打 flag（tool_error/no_answer/error/pending_confirm），用户反馈落 feedback 表；前端新增 /traces 轨迹面板 + 单轮详情（TracesPanel.tsx/RunDetail.tsx）。
  • [新增] 离线评测：新增 backend/eval/（metrics.py recall@k/MRR/nDCG + rag_eval.py + prompt_eval.py + HTML 报告 + 评测集），RAG 检索与 prompt 结构从此可量化回归。
  • [新增] 长期记忆：新增 backend/agent/memory.py（滚动摘要 + 事实抽取/召回）与 memories 表（kind='summary'|'fact'），前端左侧栏底部「我的记忆」入口（MemoryModal.tsx）。
  • [新增] Token 预算 + 上下文裁剪：新增 backend/agent/context.py，超 MAX_HISTORY_CHARS 触发滚动摘要、旧工具报文截断；prompt 分层 + 版本化（PROMPT_VERSION）。
  • [新增] 用量统计入口：左侧栏底部「用量统计」独立入口（UsageModal.tsx），与「我的记忆」并列、带状态点。
  • [调整] 前端结构：App.tsx 拆分为 src/App/ 包（index.tsx + AppHeader.tsx + Modals.tsx）。

1系统架构总览

下图由 Archify 绘制（架构图类型，inline SVG）。主对话链路自左向右：React SPA → FastAPI → LangGraph Agent → 百炼模型；V1.7.0 的语意路由与飞书安全闸门保留，V1.8.0 新增两条纵向链路——记忆链路（agent → 记忆编排 → 上下文组装，事实/摘要落 memories 表、经 token 预算 组装进模型报文）与可观测链路（每轮 trace 落 runs 表，前端 /traces 面板复盘）。

2可观测性：Trace 轨迹 + 离线评测

V1.7.0 及以前，一轮对话结束后没有留下任何可回放的记录——模型「为什么这么答」、工具「到底调了什么」、RAG「召回了哪几条」全靠人肉复述。V1.8.0 用两条链路补上测量底座：运行时 Trace（每轮落库 + 自动打标 + 前端复盘）与离线评测（RAG 检索指标 + prompt 结构回归）。

2.1 TraceCollector 采集与落库

TraceCollector 挂在 config.configurable["trace_collector"]，随图流转采集原始报文（含 kind 标记）、工具调用与召回结果，streaming.py 在轮次结束时落 runs 表并按 flag 自动打标。

# backend/tracing/collector.py —— 一轮对话的采集器
class TraceCollector:
    def __init__(self, ...):
        self.messages = []      # 原始报文（message_to_serializable 带 kind 标记）
        self.tool_calls = []    # 工具调用
        self.recalls = []       # RAG 召回
        self.flags = set()      # tool_error / no_answer / error / pending_confirm / memory_injected

    def add_flag(self, flag: str):   # graph.py 在关键节点打标，如 memory_injected
        self.flags.add(flag)
降级原则：trace 落库失败只告警、不影响主对话流程——可观测性不能反过来拖累可用性。

2.2 Trace 轨迹面板与用户反馈

前端新增 /traces 路由（TracesPanel.tsx 列表 + RunDetail.tsx 单轮详情），后端 api/routers/runs.py 提供 GET /api/runs / GET /api/runs/{run_id} / POST /api/runs/{run_id}/feedback。用户反馈落 feedback 表，与 trace 一一对应，构成后续「坏案例 → 修 prompt/阈值」的闭环。

# backend/api/streaming.py —— 落库 + 自动打标（节选）
collector = config["configurable"].get("trace_collector")
save_run(run_id, session_id, user_id, messages=collector.messages,
         tool_calls=collector.tool_calls, flags=collector.flags,
         prompt_version=collector.prompt_version)   # 失败只告警，不 raise

2.3 离线评测：RAG 指标 + prompt 结构回归

backend/eval/ 提供两类离线评测：metrics.py 实现 recall@k / MRR / nDCG@k，rag_eval.py 跑酒店检索评测（datasets/rag_hotels.json 16 问）；prompt_eval.py 对分层 prompt 做结构回归（各层是否齐全、版本号是否一致），免费可跑。

# backend/eval/metrics.py —— 检索评测指标
def recall_at_k(hits, k): ...      # 命中率：golden 是否进 top-k
def mrr(hits): ...                 # 倒数排名均值：golden 首次出现位置
def ndcg_at_k(hits, k): ...        # 排序质量：靠前命中权重更高

# 基线（rag_hotels.json 16 问，gt-rerank-v2 后）：
#   recall@5 = 0.311 / MRR = 0.620 / nDCG@5 = 0.377
#   其中 4/16 零命中，根因：宽属性问法（"性价比高的酒店"）的 golden 标注过严
先量化检索、再谈生成：RAG 评测只度量「检索环节是否把对的文档捞进 top-k」，不度量生成答案好坏——把生成层噪声与检索层问题分开，改索引/阈值/rerank 才能有对照。

3长期记忆与 Token 预算

长会话有两个老问题：token 越滚越大（历史全量塞给模型，又贵又超限）与跨会话零记忆（换会话/隔天就忘了用户是谁、偏好是什么）。V1.8.0 用「滚动摘要 + 最近原文」压 token，用「可检索事实」补跨会话记忆。

3.1 Token 预算与滚动摘要

历史超过 MAX_HISTORY_CHARS 时触发滚动摘要：把较早历史压成一段摘要（qwen-turbo），只保留摘要 + 最近 N 条原文，既省 token 又保住近期上下文细节。旧工具报文再单独截断到 OLD_TOOL_CHARS，把高开销的工具输出压扁。

# backend/agent/memory.py —— 阈值常量集中于此（一处可调、评测可对照）
MAX_HISTORY_CHARS = 12000   # 超限触发滚动摘要
SUMMARY_KEEP_TAIL = 16      # 摘要 + 最近 16 条原文
# backend/agent/context.py —— 消息裁剪
KEEP_TAIL = 16
OLD_TOOL_CHARS = 240        # 旧工具报文截断，压 token

3.2 可检索长期记忆（facts）

每轮异步从对话里抽取用户事实（qwen-turbo，fire-and-forget、失败静默降级），text-embedding-v3 向量化后存 memories 表；回答前按当前 query 向量召回 top-k（numpy 余弦，不引向量库），相似度低于 MEMORY_MIN_SIM 的丢弃。

# backend/agent/memory.py —— 事实抽取 + 召回
MEMORY_TOP_K = 3
MEMORY_MIN_SIM = 0.35
MEMORY_MAX_FACTS = 50      # 每人事实上限
FACT_DEDUP_SIM = 0.92      # 高度重复事实去重
MEMORY_MODEL = "qwen-turbo"

async def extract_facts(...): ...          # qwen-turbo 抽取，schedule_extraction 异步调度
def recall_facts(query, facts): ...        # text-embedding-v3 → numpy cosine → top-k

3.3 上下文组装与注入

assemble_model_messages() 把「system + 记忆 + 裁剪后的历史」拼成最终报文；记忆是独立的 kind="memory" SystemMessage，trace 里以 memory tag 展示，并打 memory_injected flag。实测 DashScope 支持多条/任意位置 system，不做 system 合并——trace 即真实报文，避免「你以为合并了、实际没合并」的偏差。

# backend/agent/context.py —— 组装最终模型报文
def assemble_model_messages(messages, ...):
    history = compact_history(messages)      # token 预算 + 裁剪
    facts = recall_facts(...)                # 记忆召回（失败降级为空）
    # 记忆 = 独立 SystemMessage(additional_kwargs={"kind": "memory"})
    return all_messages, {"memory_injected": bool(facts), "summarized": ...}

# backend/agent/graph.py —— _chat_node
messages, info = assemble_model_messages(...)
collector.add_flag("memory_injected")        # trace 打标
resp = await llm.ainvoke(messages)           # 无 system 合并，直接发

5关键设计决策

  • trace 落库失败只告警、不阻塞主流程：可观测性是「旁路」，不能反过来影响对话可用性；宁可少一条 trace，也不让一轮回答失败。
  • 记忆只进 LLM 输入、不写 checkpoint：LangGraph checkpoint 保持轻量（只存对话状态），跨会话记忆独立存 memories 表，删除会话时级联清理 summary、保留 fact。
  • 阈值常量集中在 memory.py 顶部：MAX_HISTORY_CHARS/MEMORY_MIN_SIM 等一处可调，评测可对照，避免散落各处拍脑袋。
  • 事实召回用 numpy 余弦、不引向量库：单用户事实 ≤50 条，O(n) 遍历足够，避免为「几个人几条事实」引入重依赖。
  • 滚动摘要 + 最近 N 条原文：摘要省 token、原文保近期上下文细节，两者互补；旧工具报文再单独截断。
  • 实测 DashScope 支持多条/任意位置 system，不做 system 合并：trace 即真实报文，杜绝「合并了但实际没合并」的隐性偏差。
  • 记忆抽取 fire-and-forget：schedule_extraction 异步跑、不阻塞本轮回答，失败静默降级。
  • RAG 评测用召回指标而非「答对了没」：先量化检索环节（recall@k/MRR/nDCG），把生成层噪声隔离出去，改索引/阈值/rerank 才有对照。
  • prompt 分层 + 版本号：PERSONA/BEHAVIOR/OUTPUT_FORMAT/CONTEXT_SECTION_TEMPLATE 分层 + PROMPT_VERSION，结构回归检查防「改了 prompt 忘了记」。

6待优化清单

问题 1：RAG 评测集过窄、golden 过严
16 问里 4 问零命中（recall@5=0.311），根因是宽属性问法（「性价比高的酒店」）的 golden 只标了少数目标。
优化方向：扩评测集 + 放宽宽属性问法的 golden，或按「属性覆盖」而非「单条命中」判定召回。
问题 2：记忆阈值缺真实查询校准
MEMORY_MIN_SIM=0.35 等为经验值，尚未用真实查询量化校准。
优化方向：用与 rag_eval 相同的方式，造一批「应召回/不应召回」的事实查询对，跑出阈值曲线再定。
问题 3：pytest 未进依赖清单
测试用例靠 .venv/bin/pip install pytest 手工装，新环境复现易漏。
优化方向：把 pytest 纳入 dev 依赖（或 requirements-dev.txt），并在 README 写明。
问题 4：SSE 断连尾部丢失
流式输出中断连时，最后一段可能丢失，trace 与前端展示不一致。
优化方向：查 streaming.py 缓冲与 sse.ts 的收尾处理，补断连补发/落库兜底。
问题 5：6 个超 300 行文件待拆分
ChatView.tsx(939)、McpModal.tsx(513)、Markdown.tsx(445)、streaming.py(356)、graph.py(343)、browser_use.py(334) 均超限（CSS 豁免）。
优化方向：按「拆分必须成包」约定逐一套目录拆分，且本次改动不再增加行数。
问题 6：事实抽取每轮都跑 qwen-turbo，开销累积
长会话每轮都异步抽一次事实，embedding + LLM 调用随轮次线性累积。
优化方向：加节流/缓存，或改为「会话结束时批量抽取一次」。
