0V1.4.0 变更摘要

V1.3.0 补齐了浏览器能力，但还缺三块：回答只有「快速模式」一档、HTTP 层散落在主入口里、知识面局限于联网搜索与飞书。V1.4.0 引入思考模式（透传 DashScope 的思维链 reasoning_content）、把 HTTP 层接口模块化（路由按业务域拆分）、并注入 RAG 检索（基于西雅图酒店数据，向量 + BM25 混合检索 + 位置过滤 + 重排）。

  • [新增] 思考模式：MODES 增加 thinking 档，ThinkingChatOpenAI 保留流式中的 reasoning_content，前端可展示思维链后再看最终答案。
  • [新增] RAG 检索：新增 backend/rag/ 包（清洗/切片/向量化/BM25/RRF/位置过滤/rerank），封装为 search_hotels 工具接入 Agent。
  • [重构] 接口模块化：HTTP 层统一收进 backend/api/，路由按 chat / sessions / mcp 三个业务域拆分，main.py 只做组装。

1思考模式：透传思维链

V1.3.0 之前只有「快速模式」（直接出答案）。V1.4.0 新增 thinking 模式，利用 DashScope 兼容接口的 enable_thinking 参数开启深度推理：模型先输出 reasoning_content（思维链），再输出 content（最终答案）。难点在于 langchain-openai 0.2.14 的流式转换默认丢弃 reasoning_content，需要子类拦截。

1.1 模式定义

MODES = [
    {"id": "fast",     "name": "快速模式", "description": "直接回答，低延迟",         "enable_thinking": False},
    {"id": "thinking", "name": "思考模式", "description": "深度思考后再回答",         "enable_thinking": True},
]
DEFAULT_MODE = "fast"

def mode_enables_thinking(mode_id):
    for m in MODES:
        if m["id"] == mode_id:
            return bool(m.get("enable_thinking"))
    return False

1.3 关键实现：保留 reasoning_content

langchain-openai 原生只映射 content / tool_calls 字段，会把思维链丢掉。因此定义 ThinkingChatOpenAI(ChatOpenAI) 子类，重写 _stream / _astream，用自定义的 _convert_chunk_with_reasoning() 把每个 delta 里的 reasoning_content 塞进 additional_kwargs。

class ThinkingChatOpenAI(ChatOpenAI):
    """保留 reasoning_content 的 ChatOpenAI 子类。"""
    def _astream(self, messages, stop=None, run_manager=None, **kwargs):
        kwargs["stream"] = True
        payload = self._get_request_payload(messages, stop=stop, **kwargs)
        response = await self.async_client.create(**payload)
        async with response:
            for chunk in response:
                generation_chunk = _convert_chunk_with_reasoning(chunk, ...)
                if generation_chunk is None:
                    continue
                yield generation_chunk

在 _convert_chunk_with_reasoning 里，核心只有一行：把 delta 上的 reasoning_content 存到消息块的 additional_kwargs["reasoning_content"]，其余沿用原生转换逻辑。

1.4 SSE 双通道推流

# streaming.py：思考模式额外推送 thinking 事件
if mode_enables_thinking(mode):
    reasoning = chunk.additional_kwargs.get("reasoning_content")
    if isinstance(reasoning, str) and reasoning:
        yield sse_event({"thinking": reasoning})   # 思维链
text = chunk.content
if isinstance(text, str) and text:
    yield sse_event({"delta": text})               # 最终答案
快速模式零影响：enable_thinking=False 时不传 extra_body，也不推送 thinking 事件，行为与 V1.3.0 完全一致。

2接口模块化：HTTP 层按业务域拆分

V1.3.0 的路由、请求体模型、流式逻辑混在一起。V1.4.0 把 HTTP 层统一收进 backend/api/ 包：路由在 api/routers/、公共流式逻辑在 api/streaming.py、请求体模型在 api/schemas.py，main.py 退化为纯组装入口。

3RAG 检索：向量 + BM25 混合检索

RAG 让 Agent 拥有「私有知识库」能力。以 csv/Seattle_Hotels.csv（152 家酒店）为语料，完整链路是：清洗 → 切片 → 向量化 → FAISS 索引 → 混合检索（BM25 + 向量 + RRF）→ 位置过滤 → Rerank 重排 → LLM 生成。检索能力封装成 search_hotels 工具，沿用关键词预筛机制按需绑定。

3.2 数据清洗与切片

原始 CSV 是 cp1252 编码，desc 里混有换行与乱码问号（撇号被替换成 ?）。清洗做转码、折叠空白、修正缩写；切片采用「一店一 chunk」策略——desc 平均约 975 字符，正好落在理想 chunk 长度，无需二次切分。

def load_hotels():
    docs = []
    with open(CSV_PATH, newline="", encoding="cp1252") as f:
        for row in csv.DictReader(f):
            name = clean_text(row.get("name", ""))
            address = clean_text(row.get("address", ""))
            desc = clean_text(row.get("desc", ""))
            text = f"{name}. {address}. {desc}"   # 一店一段 = 一个切片
            docs.append(HotelDoc(name=name, address=address, desc=desc,
                                 text=text,
                                 location=extract_locations(name, address)))
    return docs

3.4 混合检索：BM25 + 向量 + RRF

向量擅长语义，但「泳池 / 热水浴缸 / 机场班车」这类精确设施词，BM25 词法命中更准。两路各自产出「文档 → 排名」，再用 RRF（倒数排名融合）合并——只认名次、不看分数，无需归一化。

def rrf_fuse(rank_maps, k=60):
    fused = {}
    for ranks in rank_maps:
        for doc_id, rank in ranks.items():
            fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(fused.items(), key=lambda x: -x[1])

3.5 位置过滤 + Rerank 精排

纯内容匹配无法严格满足「downtown 只返回市中心」。位置过滤用邮编 + 城市名 + 名称关键词三路信号提取规范标签，查询时识别位置意图做硬过滤；Rerank 用交叉编码模型 gte-rerank-v2 对粗排前 20 名逐字精排。

5关键设计决策

  • 思考模式走「子类保留」而非改依赖：langchain-openai 流式转换丢弃 reasoning_content，通过 ThinkingChatOpenAI 子类 + 自定义 chunk 转换补齐，不动第三方库源码，升级时不破坏。
  • 快速模式是默认且零开销：enable_thinking=False 时不传 extra_body、不推 thinking 事件，保证存量用户行为不变。
  • 接口模块化按业务域而非按层：chat / sessions / mcp 各自成 router，公共流式逻辑上提到 streaming.py，请求体模型集中到 schemas.py，新接口只改对应域文件。
  • RAG 包对 Agent 完全无感：backend/rag/ 是独立可跑的检索库，只通过 search_hotels 工具与 Agent 连接，可在其它场景复用。
  • 一店一 chunk，不盲目套固定长度切分：结构化业务数据每家酒店就是天然检索单元，desc 平均 975 字符落在理想区间，避免无效切分。
  • 混合检索「召回 + 精排」两级漏斗：向量 + BM25 双塔负责广撒网（快），RRF 融合取前 20 后交给 gte-rerank-v2 交叉编码精排（慢但准），兼顾性能与精度。
  • 位置过滤用规则词典而非坐标 API：邮编 + 城市名 + 名称关键词三路信号，零外部依赖、可解释、好排查；代价是规则表外的冷门区域识别不到。
  • 索引懒加载单例 + 磁盘持久化：首次查询才构建/加载索引，152 条向量落盘 data/hotels/，重启 0.23 秒加载，不重复调用 embedding。

6待优化清单

问题 1：思考模式推理过程未做历史压缩
思维链会随 additional_kwargs 进入消息历史，长对话下 reasoning_content 累积可能撑大上下文。
优化方向：checkpoint 里不存 reasoning_content，或对历史思维链做截断，只保留最终答案。
问题 2：RAG 位置标签靠手工规则表
邮编/城市/关键词规则覆盖不了规则外的冷门社区（如 Ballard 之外的社区），且新增城市需手动补表。
优化方向：接入地理编码 API 把地址转成结构化坐标/邻域，或对无标签酒店做聚类标注。
问题 3：rerank 每次查询多一次网络调用
gte-rerank-v2 对前 20 名精排带来额外延迟，简单查询（如品牌精确匹配）收益有限。
优化方向：对 RRF 分数足够高、分歧小的查询跳过 rerank，按需触发。
问题 4：接口模块化未覆盖前端路由层
本次只拆了后端 HTTP 层，前端仍是单页结构，模型/模式选择器与聊天逻辑耦合。
优化方向：前端按「会话 / 聊天 / 设置」拆模块，与后端路由域对齐。
