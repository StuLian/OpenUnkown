0V1.5.0 变更摘要

V1.4.0 补齐了思考模式、接口模块化与 RAG 检索，但应用仍处于「裸奔」状态：运行过程不可观测、密钥要么明文要么散落在代码里、也没有一套能上生产的一键部署方案。V1.5.0 把这三块一次性补上：接入 LangSmith 全链路追踪、建立「ignore + 加密」双层密钥治理（登录 + JWT + 信封加密）、并沉淀出systemd + Nginx 的集成部署方案。

  • [新增] LangSmith 追踪：langsmith 依赖 + .env 环境变量即开即用，零埋点自动上报 agent / LLM / 工具调用，trace 附带 tags 与 metadata。
  • [新增] 登录与多用户隔离：本地账号密码 + JWT 会话，密码走 RSA-OAEP 传输加密 + PBKDF2 落库散列，会话 / MCP / ApiKey 全部按用户隔离。
  • [新增] 密钥加密体系：ApiKey 信封加密落库、MCP env 主密钥加密、三把服务端密钥文件 chmod 600 且全部进 .gitignore。
  • [新增] 集成部署方案：deploy/ 目录沉淀 Nginx + systemd + 本地/服务器幂等一键脚本 + 阿里云 SOP。

1LangSmith 追踪配置

V1.4.0 的 Agent 执行过程是「黑盒」：LLM 输入了什么、调用了哪些工具、每步耗时多少，只能在服务端日志里翻。V1.5.0 接入 LangSmith，利用 LangGraph 原生集成的特性做到零埋点——只要配置环境变量，agent 执行、LLM 调用、工具调用就会自动上报，无需在业务代码里加任何 trace 代码。

1.1 配置方式：纯环境变量

# .env（复制 .env.example 后填写）
# 在 https://smith.langchain.com 创建 API Key
LANGSMITH_API_KEY=lsv2_pt_your_api_key_here
LANGSMITH_TRACING=true
# 追踪写入的项目名（可选，默认用应用名 OpenUnknown）
# LANGSMITH_PROJECT=OpenUnknown
# 自托管 LangSmith 才需要接入地址，SaaS 云端无需设置
# LANGSMITH_ENDPOINT=http://your-langsmith-host:1984
变量必填说明
LANGSMITH_API_KEY是LangSmith API Key（lsv2_pt_...）
LANGSMITH_TRACING是设为 true 才自动上报
LANGSMITH_PROJECT否项目名，缺省用应用名 OpenUnknown
LANGSMITH_ENDPOINT否自托管接入地址，SaaS 不需要

1.2 关键：.env 必须尽早加载

LangSmith 依赖 LANGCHAIN_* / LANGSMITH_* 环境变量在 第三方库 import 时生效。而 dashscope 在 import 时会固化 api_key，因此 load_dotenv 必须放在任何会读环境变量的 import 之前。V1.5.0 在 backend/config.py 顶部统一加载，并给项目名一个兜底默认值。

# backend/config.py —— 必须在 import dashscope 等库之前执行
from dotenv import load_dotenv
load_dotenv(Path(__file__).resolve().parent.parent / ".env", override=False)

# 未显式指定项目名时，默认用应用名，便于控制台区分
if not os.getenv("LANGSMITH_PROJECT") and not os.getenv("LANGCHAIN_PROJECT"):
    os.environ["LANGSMITH_PROJECT"] = APP_NAME
踩坑记录：.env 在 backend/ 的上一级（项目根目录），而非 backend 目录内；若加载晚于 dashscope 的 import，环境变量对已被固化的库无效。

1.4 附加 tags 与 metadata

光有 trace 不够，还得能在控制台按「谁 / 哪个模型 / 哪种模式」过滤。每次请求在 RunnableConfig 上附带 tags 与 metadata，LangSmith 自动把它们挂到该请求产生的整条 trace 上。

# backend/api/streaming.py
config = {
    "configurable": { "thread_id": ..., "model": model, "mode": mode, ... },
    # tags 便于过滤；metadata 便于按字段检索
    "tags": ["openunknown", f"user:{user_id}", f"model:{model}", f"mode:{mode}"],
    "metadata": {
        "session_id": session_id,
        "user_id": user_id,
        "user": username,
        "model": model,
        "mode": mode,
    },
}
效果：一次对话的完整链路（提示词、模型输出、工具调用、token 用量、耗时）都在 LangSmith 面板可见，排障从「翻本地日志」升级为「按 user / model / mode 检索 trace」。

2密钥治理：ignore 与加密双层防线

V1.4.0 之前，模型 ApiKey 靠环境变量 / 本地文件兜底，MCP 的 env 里还躺着明文令牌，仓库公开后等于裸奔。V1.5.0 把密钥治理拆成两条线：「不该进库的一律 ignore」（.gitignore），「必须存下来的一律加密」（信封加密 + 服务端主密钥），并顺带引入登录与多用户隔离，让密钥归属到具体用户。

2.1 .gitignore：从源头挡住敏感文件

# 环境变量（模板可提交，真实值不进库）
.env
.env.*
!.env.example

# 服务端密钥（JWT 签名 / 信封加密主密钥 / 密码传输私钥）
data/.app_secret
data/.app_master_key
data/.app_auth_key

# 私钥 / 证书（仓库是公开的，绝不能入库）

2.2 三把服务端密钥：自动生成 + chmod 600

服务端运行需要三把密钥，全部首次使用时自动生成、落到 data/ 下并 chmod 600，永不进 git、永不出服务端进程边界。

文件用途丢了会怎样
data/.app_secretJWT 会话签名密钥（HS256）全员需重新登录
data/.app_master_key信封加密主密钥（Fernet）ApiKey / MCP env 解不开，需重填
data/.app_auth_key登录密码 RSA 私钥（2048 位）需重新生成，影响登录解密

2.3 登录密码：传输加密 + 落库散列

密码在传输层用 RSA-OAEP-SHA256 加密，在存储层用 PBKDF2-SHA256 散列——请求体、日志、抓包里都不出现明文，落库也只有散列值。前端提交前先拿一次性 nonce + 公钥，防重放。

flowchart TD
    A["前端 GET /api/auth/challenge"] --> B["下发 RSA 公钥 + 一次性 nonce"]
    B --> C["前端 RSA-OAEP-SHA256 加密密码"]
    C --> D["POST /login 或 /register（无明文密码）"]
    D --> E["服务端 consume_nonce 校验防重放"]
    E --> F["私钥解密 → PBKDF2 散列校验"]
    F --> G["签发 JWT（7 天有效）"]
      
# backend/security/challenge.py —— nonce 一次性 + 有效期 + 内存上限
_NONCE_TTL_SECONDS = 300        # nonce 5 分钟过期
_MAX_NONCES = 10_000            # 防恶意刷 challenge 撑爆内存

# backend/security/crypto.py —— 密码只存 PBKDF2-SHA256 散列
dk = hashlib.pbkdf2_hmac("sha256", password.encode(), salt.encode(), 200_000)

2.4 ApiKey：信封加密，明文永不落库

模型服务 ApiKey 不再走环境变量 / 本地文件兜底，而是登录后在「模型设置」填写，加密落库、立即生效、不回显明文。加密采用信封加密（Envelope Encryption）：每个用户一把随机 DEK 加密 ApiKey，DEK 本身再用服务端主密钥包裹——这样主密钥泄露也不会直接暴露 ApiKey，且服务重启后 DEK 可从磁盘恢复，无需重新登录。

flowchart TD
    subgraph DB["SQLite 落库"]

        B["users.dek_ciphertext = Fernet(DEK, master_key)"]
    end
    subgraph DISK["磁盘密钥"]
        M["data/.app_master_key（chmod 600）"]
    end
    DEK["每用户随机 DEK（Fernet 密钥）"] --> A
    DEK --> B
    M --> B
      
# backend/auth/service.py —— 信封加密核心
def save_api_key(user_id, platform, api_key):
    dek = _ensure_user_dek(user_id)               # 每用户 DEK
    ciphertext = crypto.encrypt_apikey(api_key.strip(), dek)   # ApiKey 用 DEK 加密
    user_store.set_user_api_key(user_id, platform, ciphertext)

def resolve_api_key(user_id, platform):
    ciphertext = user_store.get_user_api_key_cipher(user_id, platform)
    dek = _ensure_user_dek(user_id)               # DEK 由主密钥解出，重启可恢复
    return crypto.decrypt_apikey(ciphertext, dek)

2.5 MCP env：敏感令牌主密钥加密

MCP Server 的 env 可能含访问令牌，落库前用服务端主密钥整体加密，读取时解密；对历史明文 JSON 做了幂等迁移与读取兼容。

# backend/store/mcp.py
def _encrypt_env(env: dict) -> str:
    return encrypt_secret(json.dumps(env))      # 用主密钥加密整个 env

# backend/store/db.py —— 迁移：把历史明文 env 一次性加密
if env.startswith("{"):
    UPDATE mcp_servers SET env = encrypt_secret(env) WHERE id = ?
安全边界：登录密码的 RSA 传输加密保证「请求体 / 日志 / 抓包不含明文」，但无法抵御已完全控制浏览器本地的攻击者（密码加密前本就以明文存在于输入框）；传输层安全仍依赖 HTTPS（TLS）。

3集成部署方案

V1.4.0 只有本地 uvicorn 一条路。V1.5.0 沉淀出「子域名」部署方案 C：主域名首页放 OSS，聊天应用放在 ECS 的子域名 chat.<域名> 上，前端由 FastAPI 直接托管（无单独前端部署），数据库用 SQLite（不需要 MySQL/Redis），模型 ApiKey 由用户界面填写、加密落库、不进环境变量。

3.5 Nginx：SSE 流式必须关缓冲

聊天是 SSE 流式返回，Nginx 默认会缓冲响应，导致「卡到最后才一起返回」。模板里两处关键配置缺一不可。

# deploy/nginx-openunknown.conf
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;       # 关键：SSE 流式必须关缓冲
    proxy_cache     off;
    proxy_read_timeout  300s;  # 思考模式长响应不能提前断开
}
踩坑记录：proxy_buffering off 漏配，流式会卡到最后才返回；SELinux Enforcing 下访问 502 需执行 setsebool -P httpd_can_network_connect 1；国内 ECS 装依赖建议走阿里云 pip 镜像。

5关键设计决策

  • LangSmith 零埋点，把元信息挂在 config 上：不侵入 agent 图代码，只在 stream_answer 组装 RunnableConfig 时带上 tags/metadata，靠 LangGraph 原生集成自动上报，埋点成本趋近于零。
  • load_dotenv 必须抢在第三方 import 前：dashscope import 时会固化 api_key，LangSmith 依赖 import 时读取环境变量，因此统一在 config.py 顶部加载 .env，一个入口避免顺序踩坑。
  • 密钥治理「ignore 优先，加密兜底」：能不入库的先靠 .gitignore 挡住（.env、密钥文件、私钥、数据库）；必须持久化的再加密（ApiKey 信封加密、MCP env 主密钥加密），两条防线各管一段。
  • ApiKey 信封加密而非单层加密：每用户随机 DEK 加密 ApiKey，DEK 用主密钥包裹。主密钥与 DEK 分层，主密钥泄露不直接暴露 ApiKey，且 DEK 落库后重启可恢复，免去「换 key 重登」。
  • 密码「传输加密 + 落库散列」双重保护：传输层 RSA-OAEP 加密 + 一次性 nonce 防重放，存储层 PBKDF2-SHA256（20 万次迭代）散列；明文只在浏览器输入框与服务端解密瞬间短暂存在。
  • 多用户隔离用「thread_id 命名空间」：checkpoint 的 thread_id 用 {user_id}:{session_id}，会话 / MCP / ApiKey 全部挂 user_id，即使会话 id 相同也不串数据。
  • ApiKey 无兜底、随用户配置：模型服务 ApiKey 不再走环境变量 / 本地文件兜底，登录后界面填写、加密落库、立即生效；未配置的用户在界面被拦截，后端也直接返回错误事件。
  • 部署脚本「本地打包 + 服务器幂等」两段式：本地 deploy_local.sh 负责打包上传（rsync 排除敏感目录），服务器 deploy.sh 负责安装且幂等可重复执行，更新与首次迁移（--with-data）分离。
  • 首次迁移用 SQLite 一致性备份：sqlite3 ".backup" 而非直接 cp 单文件，避免 WAL 模式下拷出不一致的库；deploy.sh 只在服务器无库时才恢复数据包。
  • systemd 服务最小权限硬化：NoNewPrivileges=true + PrivateTmp=true + 专用非登录用户，uvicorn 只监听 127.0.0.1，由 Nginx 做 TLS 终止与反向代理。

6待优化清单

问题 1：LangSmith 上报的敏感字段未脱敏
trace 里会完整记录提示词与模型输出，若用户输入或 MCP 工具返回夹带敏感信息（如某个工具误回显 token），会原样进 LangSmith。
优化方向：对工具输出 / 消息内容做敏感字段扫描与脱敏后再上报，或对特定字段配置 redact 规则。
问题 2：JWT 无状态退出，服务端无法吊销
/api/auth/logout 只是让客户端删 token，服务端不维护会话状态，token 被盗后 7 天内仍有效。
优化方向：引入 token 黑名单 / 短时 access + refresh 双令牌，或把签发时间戳纳入校验做强制下线。
问题 3：主密钥是「单点」
.app_master_key 丢了 ApiKey / MCP env 全部解不开，且它本身是明文文件，仅靠 chmod 600 与文件系统权限保护。
优化方向：接入 KMS / 密钥托管，或对主密钥做硬件加密与定期轮换（re-encrypt）。
问题 4：部署仅覆盖阿里云 dnf 系单机
deploy.sh 虽做了 dnf/apt 分支，但尚未覆盖 Docker / 多实例 / 负载均衡场景，SQLite 单机也无法横向扩容。
优化方向：出 Docker Compose 编排与容器镜像，数据库按需迁移到 PostgreSQL 以支持多实例。
问题 5：ApiKey 仅支持单平台
数据结构已为多平台预留（PLATFORMS / user_api_keys(user_id, platform)），但当前仅百炼一个平台可用。
优化方向：补齐前端平台选择器与多平台切换，让 ApiKey 按平台分表生效。
