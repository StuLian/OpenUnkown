0V1.1.0 变更摘要

相较 V1.0.0（基础问答 + 多会话持久化），本次迭代围绕「让 Agent 真正能干活」展开，新增三层工具体系与模型选择能力。

  • [新增] FC（Function Calling）：内置工具包 tools/，首个工具 get_weather 走 Open-Meteo API。
  • [新增] MCP（Model Context Protocol）：拆出 mcp/ 包（client/converter/manager），动态加载用户配置的 MCP Server 工具；前端管理 UI 支持增删改、启停、测试、JSON 导入。
  • [新增] Skill（飞书 CLI 集成）：把 lark-cli 包装成 lark_cli 工具，启动时拉取 27 个飞书 skill 描述注入 system prompt，让模型通过单一工具操作飞书全业务域。
  • [新增] 模型选择：前端下拉选择器，后端按请求透传 model 到 graph config，同一会话不同轮次可用不同模型。
  • [新增] 工具调用透明化：前端 badge 显示「调用中 → 已返回」，按 tool_call_id 精准匹配，支持同名工具并发多次调用。
  • [待优化] MCP 每次请求都冷启动子进程拉工具列表，性能开销大。
  • [待优化] 飞书 skill 描述每轮都拼进 system prompt，固定 token 开销约 3700 字。

1项目概览

OpenUnknown 是一个以 LangGraph 为 Agent 框架搭建的 Web 侧问答系统。V1.1.0 在基础多轮问答之上，构建了 FC + MCP + Skill 三层工具体系，并支持运行时切换模型，让 Agent 既能调用本地内置工具，也能动态接入用户配置的外部 MCP Server，还能通过飞书 CLI 操作飞书全业务域。

5FC：内置工具包

FC（Function Calling）是最基础的工具层，每个工具是一个用 @tool 装饰的原子函数，模型按 description 语义匹配调用。

5.1 包结构

backend/agent/tools/
├── __init__.py      # 注册表：TOOLS = [get_weather, lark_cli]
├── weather.py       # get_weather (Open-Meteo API)
└── lark_cli.py      # 飞书 CLI 包装 (见第 7 节 Skill)

新增内置工具的流程：在 tools/ 下建模块 → 写 @tool 函数 → 在 __init__.py 的 TOOLS 列表注册。graph.py 只 from backend.agent.tools import TOOLS，不直接依赖具体工具文件。

5.2 get_weather 工具

走 Open-Meteo 的免费天气 API：先用 geocoding-api 把城市名转经纬度，再调 forecast 拿当前天气。返回结构化文本（地点/天气/气温/湿度/风速），WMO 天气代码映射为中文。

description 里明确写了「用户问天气、气温、是否下雨时必须调用本工具，不要凭记忆编造」，这是引导模型主动调用的关键。

6MCP：动态外部工具

MCP（Model Context Protocol）让用户能配置任意外部 MCP Server，Agent 启动时动态拉取其工具列表并转成 LangChain StructuredTool，与内置工具一起绑定给模型。

6.1 包结构

文件职责
mcp/__init__.py对外暴露 get_enabled_mcp_tools、test_mcp_server、execute_mcp_tool
mcp/client.py连接上下文管理，支持 stdio（本地子进程）和 sse/http（远程服务）两种方式
mcp/converter.py把 MCP 工具的 JSON Schema 转成 Pydantic 模型，用于参数校验和文档生成
mcp/manager.py核心逻辑：拉取工具列表、执行工具调用、组装 StructuredTool

6.3 调用流程

模型在 chat 节点决定调用某个 MCP 工具后，LangGraph 路由到 tools 节点，按 tool_call_id 找到对应 StructuredTool 执行。执行时闭包会再建一次连接调 session.call_tool()，拿到结果后拼成 ToolMessage 回到 chat 节点。

待优化问题 1：当前每次请求都会重新连接所有已启用 MCP Server 拉取工具列表（冷启动 npx 子进程），开销大。一次完整 MCP 调用，同一个 Server 会被连接 2 次（拉列表 + 执行）。优化方向：启动时拉一次缓存工具列表，定时刷新，执行时再连。

6.4 工具描述注入来源标签

为了让模型区分同名工具归属，MCP 工具的 description 前会自动加 [MCP: 服务名] 前缀。例如高德的天气工具描述为 [MCP: amap-maps] 根据城市名称或者标准adcode查询指定城市的天气，模型看到「用高德查」时就能优先匹配。

6.5 前端管理 UI

侧边栏底部「MCP 扩展管理」入口，弹窗支持：已配置服务列表（启停/测试/编辑/删除）、添加服务（stdio/sse 表单）、JSON 批量导入（兼容 Claude Desktop / Cursor 格式）。配置持久化在 mcp_servers 表。

7Skill：飞书 CLI 集成

Skill层处理「一个 CLI 暴露大量能力」的场景。飞书 lark-cli 覆盖 IM/日历/文档/表格/任务/邮件等 27 个业务域，如果每个能力做成独立工具会爆炸，所以采用单一工具 + skill 描述注入的方式。

7.1 设计思路

  • 单一工具 lark_cli：接收 command 字符串，通过子进程执行 lark-cli 命令。
  • skill 描述注入 system prompt：启动时调 lark-cli skills list 拉取 27 个 skill 描述（约 3700 字），拼进 system prompt，让模型知道有哪些 domain 可用、每个 domain 对应什么能力。
  • 认证独立：飞书凭证由 lark-cli 自己管理（本地加密存储，~/Library/Application Support/lark-cli/），与 OpenUnknown 的 ApiKey 完全解耦。Agent 用「当前登录用户」的身份操作飞书。

7.3 prompt 拼接策略

_get_system_prompt(model_name) 把三部分拼起来：

base prompt
(含模型身份, 每次构建) + lark skill 描述
(启动时缓存, 约 3700 字) = 完整 system prompt

贵的、跟模型无关的部分（lark skill 列表）缓存一次；便宜的、跟模型有关的部分（身份声明）每次构建，保证切模型后身份问答准确。

待优化问题 2：飞书 skill 描述每轮请求都会拼进 system prompt 发给模型，固定 token 开销约 3700 字。优化方向：按需注入（用户消息出现飞书关键词时才拼）、精简描述（每条压到 30 字）、或改成工具描述（模型需要时再调工具拉详细能力）。

8.3 关键实现点

  • get_llm(model_name)：按模型名参数化，lru_cache(maxsize=8) 让每个模型实例只构建一次，切换很快。
  • 身份指令放在历史消息之后：在 _chat_node 里，先发 system prompt + 历史消息，再插一条「【本轮实际模型】xxx」的 SystemMessage，避免旧回复里的模型名覆盖本轮选择。
  • 前端回显实际模型：每轮回复下方显示「模型 xxx · 本轮 Tokens：...」，方便确认后端真正用的是哪个模型。
  • 后端兜底校验：chat() 端点用 is_valid_model() 校验，非法 model 回退到 DEFAULT_MODEL。
历史消息（含之前模型生成的回复）仍会作为上下文保留，这是 LangGraph checkpointer 的标准行为。切换模型只影响本轮生成，不改写历史。

9工具调用透明化

为了让用户知道 Agent 是否真的调了工具，前端在回答气泡上方显示工具调用 badge，状态从「调用中」变「已返回」。

9.1 SSE 事件

后端在 _stream_answer 里监听 tools 和 chat 节点，推送两类事件：

事件触发时机字段
{"tool_call": {id, tool, args}}模型决定调用工具时id=tool_call_id, tool=工具名
{"tool_result": {id, tool, output}}工具执行完毕时output截前 300 字

9.2 前端 badge 匹配

前端按 tool_call_id 匹配（不是按工具名），支持同名工具并发多次调用。流式下同一个 tool_call 会分多个 chunk 到达，前端按 id 去重，只在首次到达时创建 badge。

早期版本按工具名匹配，导致同一轮多次调用 lark_cli 时，后创建的 badge 覆盖先创建的，先创建的一直卡在「调用中」。改为按 id 匹配后修复。

10流式输出是怎么做的

采用 SSE（Server-Sent Events）而非 WebSocket，因为问答只需服务端单向推送，SSE 基于普通 HTTP、实现更轻，且配合 LangGraph 的 stream_mode="messages" 天然就是 token 级增量。V1.1.0 在此基础上额外推送工具调用事件。

10.1 时序图

sequenceDiagram
    autonumber
    participant U as 浏览器 (app.js)
    participant F as FastAPI (main.py)
    participant G as LangGraph (graph.py)
    participant M as 所选模型

    U->>F: POST /api/chat { message, session_id, model }
    F-->>U: data: {"model": "qwen-turbo"}
    F->>G: graph.astream(stream_mode="messages")
    G->>M: await llm.ainvoke(messages)
    G-->>F: tool_calls chunk
    F-->>U: data: {"tool_call": {id, tool, args}}
    G-->>F: tools 节点 ToolMessage
    F-->>U: data: {"tool_result": {id, tool, output}}
    loop 每个 token 增量
        M-->>G: token chunk
        G-->>F: (chunk, meta)
        F-->>U: data: {"delta": "..."}
        U->>U: 累加渲染(打字机效果)
    end
    F-->>U: data: {"usage": {...}}
    F-->>U: data: [DONE]

10.2 关键实现点

  • 后端 graph.astream(stream_mode="messages") 逐 token 产出增量，只保留 chat 节点的内容推给前端。
  • 每个增量打包为 data: {"delta": "..."}\n\n 的 SSE 消息，用 StreamingResponse(media_type="text/event-stream") 持续写入连接。
  • 前端用 resp.body.getReader() 循环读取字节流，按 \n 拆行解析；用 buffer 处理跨分片的"半行"问题。
  • 结束前回传 {"usage": {...}} token 用量，最后发 data: [DONE] 收尾。

10.3 中断机制

前端用 AbortController 中断 fetch；后端在每个 chunk 前检查 request.is_disconnected()，客户端断开即 break，async 生成器关闭会真正取消底层模型请求，避免空跑浪费 token。

11持久化是怎么做的

所有持久化数据集中存于 data/openunknown.db（SQLite，开启 WAL 模式），由两套逻辑共用同一个数据库文件管理，以 session_id 作为贯穿两者的关联键。V1.1.0 新增 mcp_servers 表存 MCP 配置。

11.1 三类数据

数据管理者数据表作用
对话状态AsyncSqliteSavercheckpoints / writes完整多轮对话状态，支持恢复上下文
会话元数据store.pysessions标题与时间戳，用于侧边栏列表与排序
MCP 配置store.pymcp_servers用户配置的 MCP Server（name/type/command/url/enabled 等）

11.2 关键点

  • thread_id = session_id：checkpoint 以 thread_id 隔离会话，与元数据表的 id 一一对应。
  • 首条消息自动建会话：/api/chat 收到消息时 create_session（已存在则忽略），标题取首条消息前 24 字。
  • 异步 checkpointer：AsyncSqliteSaver 配合 aiosqlite，与节点的 ainvoke、接口的 astream 全链路异步。
  • 删除级联：删除会话时同时清理 sessions 与 checkpoint 表中对应 thread_id 的数据。

14关键设计决策

  • 三层工具体系：FC 处理原子能力、MCP 处理外部协议工具、Skill 处理「一个 CLI 暴露大量能力」的场景，三者最终都汇入 bind_tools。
  • SSE 而非 WebSocket：问答为单向推送场景，SSE 更轻量、契合 LangGraph stream_mode 天然增量。
  • 模型选择请求级：同一会话不同轮次可用不同模型，get_llm 按模型名缓存，切换零成本。
  • 身份指令放在历史消息之后：避免旧回复里的模型名覆盖本轮选择，保证切模型后身份问答准确。
  • 工具 badge 按 tool_call_id 匹配：支持同名工具并发多次调用，不互相覆盖。
  • 飞书认证独立：由 lark-cli 自行管理本地加密凭证，OpenUnknown 不碰飞书密钥。
  • 异步贯穿：节点 ainvoke + astream + AsyncSqliteSaver，保证客户端断开可真正中断底层请求。
  • 消除 fallback 思路：ApiKey 统一从 get_default_api_key 读取，未配置即显式报错，不堆叠兜底逻辑。

15待优化清单

问题 1：MCP 每次请求都冷启动子进程拉工具列表
现状：每次 _chat_node 调用都会重新连接所有已启用 MCP Server 拉取工具列表，npx 冷启动 Node 进程开销大；一次完整 MCP 调用同一 Server 会被连接 2 次（拉列表 + 执行）。
优化方向：启动时拉一次缓存工具列表，定时刷新；执行时再连。或维持长连接复用 session。
问题 2：飞书 skill 描述每轮都拼进 system prompt
现状：约 3700 字的 skill 描述每轮请求都拼进 system prompt 发给模型，固定 token 开销。从实测看，三轮短问答输入 token 都在 4.7 万左右，其中包含这部分固定开销 + 旧会话历史。
优化方向：按需注入（用户消息出现飞书关键词时才拼）、精简描述（每条压到 30 字）、或改成工具描述（模型需要时再调工具拉详细能力，但会多一轮工具调用）。
